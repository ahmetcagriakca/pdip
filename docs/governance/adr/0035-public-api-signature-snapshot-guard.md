# ADR-0035: Public-API signature-snapshot guard for the 1.0 contract

- **Status:** Accepted
- **Date:** 2026-04-25
- **Deciders:** pdip maintainers
- **Tags:** testing, ci, quality, governance, api
- **Extends:** [ADR-0034](./0034-one-zero-readiness-criteria.md)
  (1.0 readiness — §5 left this guard layer as a follow-up)

## Context

[ADR-0034](./0034-one-zero-readiness-criteria.md) §5 describes
public-surface enforcement in three layers and explicitly defers the
third — the *signature guard* — to its own ADR. The first two have
shipped:

1. **Drift guard** —
   `tests/unittests/public_api/test_public_api_contract.py` asserts
   every package in `EXPECTED_PUBLIC_SURFACE` declares `__all__`,
   that `__all__` matches the documented set, that every name
   resolves on the module, and that no name is duplicated.
2. **Coverage guard** —
   `RuleADR0034NoUndocumentedTopLevelPackage` in
   `tests/unittests/quality_guard/test_conventions.py` ensures every
   directory directly under `pdip/` is either documented or on an
   internal-package allowlist.

What neither guard catches today is a *signature* change: a public
class whose `__init__` parameters change, a public function with a
new positional argument, a return-type annotation flip. Any of those
breaks the SemVer guarantees from ADR-0034 §2 silently — `__all__`
still lists the symbol, `docs/public-api.md` still references it,
the package still imports, but downstream callers break at runtime.

The candidate baseline sources are:

- **PyPI sdist** of the previous minor — fetched at CI time,
  introspected for signatures, diffed against the working tree.
  *Pro:* Reflects the actual artefact users installed. *Con:*
  Network dependency in every PR build (unavailable on offline
  forks, brittle on PyPI outages); requires sandboxing the older
  source so its imports don't pollute the test environment.
- **Git tag introspection** — checkout the previous minor's tag in
  CI, diff. *Pro:* No network. *Con:* Requires a clean second
  worktree, brittle with squash-merge history, costly on Windows
  runners, and tooling differences across CI matrix cells (the
  shallow-clone default would have to change).
- **Checked-in snapshot** — a JSON file in the repo whose entries
  are `{"<package>.<symbol>": "<rendered signature>"}`. *Pro:*
  Self-contained, fully reviewable in PR diff, no network or
  multi-checkout dance, works identically on every CI cell.
  *Con:* Requires a contributor to regenerate the snapshot when
  intentionally changing a public signature (and to follow the
  ADR-0034 §3 deprecation cycle for removals).

## Decision

### 1. Baseline source: checked-in JSON snapshot

The signature baseline lives at
[`docs/public-api-signatures.json`](../../public-api-signatures.json).
It is generated by introspecting the public surface defined in
`EXPECTED_PUBLIC_SURFACE`. Each entry is a single string in a stable
text form:

```json
{
  "pdip.cqrs.Dispatcher": "class Dispatcher(self, service_provider: pdip.dependency.provider.ServiceProvider)",
  "pdip.observability.get_tracer": "def get_tracer(name)",
  "pdip.exceptions.OperationalException": "class OperationalException(self, *args, **kwargs)"
}
```

The file is checked in. Every PR that touches a public symbol's
signature also updates this file as part of the same diff. The
snapshot is the contract; CI is its enforcer.

The file is sorted by key so unrelated PRs do not produce conflicting
diffs, and the rendered form is computed deterministically (no
function-default repr that captures memory addresses).

### 2. Rendered signature format

For each name `<symbol>` in `EXPECTED_PUBLIC_SURFACE[<package>]`:

- **Class** → `"class <symbol>" + str(inspect.signature(symbol.__init__))`.
- **Function** → `"def <symbol>" + str(inspect.signature(symbol))`.
- **Anything else (constants, type aliases)** → `"<repr(value)>"`.

`inspect.signature` produces a stable string with parameter names,
default values, and (where present) annotations. We do not strip
annotations: an annotation flip from `int` to `str` is a real
contract change.

The format is human-reviewable on purpose — a maintainer reading the
diff can see exactly what changed without parsing JSON values.

### 3. Diff algorithm — fail on any drift

The new quality_guard rule
`RuleADR0035PublicApiSignatureSnapshotMatches` in
`tests/unittests/quality_guard/test_conventions.py`:

1. Loads `docs/public-api-signatures.json`.
2. Re-introspects the live public surface using the format from §2.
3. Computes three diff sets: **added**, **removed**,
   **changed-signature**.
4. Fails CI when **any** of the three is non-empty, listing the
   affected keys with the snapshot value and the actual value
   side by side.

A change of any kind is a *deliberate* event: the contributor must
update the snapshot to match (regen via the helper from §5), and the
reviewer reads the diff to confirm intent. There is no soft-warning
path; that has historically created technical debt that the
deprecation cycle from ADR-0034 §3 was designed to avoid.

### 4. Removal still needs ADR-0034 §3

A removal that updates the snapshot in the same PR closes this
guard but **does not** satisfy ADR-0034 §3, which requires a
`DeprecationWarning` to have shipped in a prior minor. Reviewers
catch unauthorised removals; ADR-0034 §3 is the spec, and a future
ADR may automate the warning-bearing-prior-release check (out of
scope here).

### 5. Regeneration helper

A small standalone script —
[`scripts/regenerate_public_api_signatures.py`](../../../scripts/regenerate_public_api_signatures.py)
— prints the snapshot dictionary in the same canonical form the
guard reads. The contributor runs it after intentionally changing a
public signature:

```bash
python scripts/regenerate_public_api_signatures.py > docs/public-api-signatures.json
```

The script is *not* invoked by CI; it is a developer convenience.
The snapshot file is the source of truth.

### 6. Stability of the snapshot itself

The snapshot file format (a flat JSON object keyed by
`<package>.<symbol>`) is part of the contract this ADR establishes.
Changing the format (e.g. adding nested per-parameter detail)
requires its own ADR — at that point we'd also rerun the guard
against the prior format to avoid silent regressions.

## Consequences

### Positive

- A signature break on a public symbol now fails CI at the same
  rigour as a missing test or a coverage drop. The 1.0 SemVer
  promise has machine teeth, not just review teeth.
- The snapshot is self-contained: no network, no second checkout,
  no per-platform fragility. Works the same on every Python × OS
  cell in the matrix.
- The diff in a PR that intentionally changes a public signature
  is human-readable — reviewers see the change in
  `docs/public-api-signatures.json` next to the source change.

### Negative

- One more file to keep in sync alongside `__all__`,
  `docs/public-api.md`, and `EXPECTED_PUBLIC_SURFACE`. The
  regeneration script and the failure message both point at the
  same fix path so the cost stays bounded.
- The first time a `default=<object>` value is involved, the
  rendered form may include `repr(object)` which can be unstable
  across runs. We do not currently use such defaults in the
  public surface; the guard will surface the case the first time
  it appears and the contributor will pick a stable representation
  (a sentinel string, a module-level constant) at that point.
- Annotations using forward-string references render as the
  string. That is intentional — it pins the resolved form rather
  than the lookup target.

### Neutral

- The snapshot grows linearly with the public surface. At 1.0 we
  expect ~30-50 entries; at 100 entries the file is still a
  human-reviewable diff.
- Renaming a public symbol shows as one removal + one addition in
  the diff. Reviewers verify intent; no algorithmic deduplication
  is needed.

## Alternatives considered

### Option A — PyPI sdist baseline

- **Pro:** Reflects what users actually installed.
- **Con:** Network dependency, sandbox cost, per-cell flakiness
  on outages, slower CI by minutes per build.
- **Why rejected:** Cost outweighs the small marginal precision
  win — `main` on PyPI is the snapshot at the moment of release,
  which is what the checked-in snapshot already is.

### Option B — Git tag introspection

- **Pro:** No network.
- **Con:** Multi-checkout dance, fragile across squash-merged
  history, doesn't degrade gracefully on shallow clones, would
  need bespoke logic per CI cell to handle Windows path quirks.
- **Why rejected:** Same cost-outweighs-benefit argument as Option
  A, with extra fragility.

### Option C — Mutation-style nuanced rules ("warn on annotation flip,
fail on parameter rename")

- **Pro:** More expressive.
- **Con:** Every "warn" path is a future debt accumulator;
  ADR-0034 §3 already tells contributors how to land any change
  cleanly (deprecate, then remove). A binary fail-or-pass match
  the discipline.
- **Why rejected:** ADR-0027 §3's diff-cover gate took the same
  hard-line "100 % or fail" stance for the same reason.

## Follow-ups

- Subsequent ADR (post-1.0) for automating the
  warning-bearing-prior-release check that ADR-0034 §3 currently
  enforces in review.
- If the snapshot ever exceeds ~200 entries and PR diffs become
  unreviewable, revisit the format with a new ADR that allows
  per-package nested files (one snapshot file per public package).
